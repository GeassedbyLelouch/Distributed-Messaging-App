ML-KEM-Braid — local verification harness

Two real sessions in one process. Every key, signature, encapsulation, nonce, frame and error below was produced live by mlkb-crypto, mlkb-wire and mlkb-protocol. Nothing on this page is mocked or canned.

Local verification tool. NOT a shipping component. Bound to 127.0.0.1 only. No persistence, no authentication, no transport security.

1 · Identities

Alice — IdentityId
Bob — IdentityId

IdentityId = SHA-256(ik_x25519 ‖ SHA-256(ik_mldsa)) — a hybrid identity (X25519 + ML-DSA-65), parent §3.5. The 1952-byte ML-DSA key is deliberately not on the wire, which is what makes this computable from InitialMessageV2 alone.

Both prekey signatures are verified before any key in the bundle is used (parent §4.3), each under its own signature context (M1 §E.2) — which is what stops a signed X25519 prekey being lifted into the PQ-prekey slot. The EnrolmentProof in the bundle is not verified here: its issuer keys are a pinned set and the check belongs to mlkb-policy (M1 §F). Its signature in this demo is a structurally valid placeholder, and is never presented as valid.

session_id = HKDF-Expand(SK, "MLKEMBraid/sid/v2", 32). Each side computed it independently from its own SK; SK itself never leaves RootKey and there is no accessor for it, so this equality is the only observation of root-key agreement either end can make. ikm = F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4 ‖ KEM_SS (M1 §C.1) — four X25519 legs and one real ML-KEM-1024 encapsulation. No root key exists in this codebase without the PQ leg: derive_sk consumes a KemSharedSecret by value and the only source of one is a real ML-KEM operation (parent §4.1).

  session_id. It covers exactly that, and no more: Session
  exposes no reader for the root key, either chain key, the frame keys or the
  ratchet keypairs, and this tool is not going to add one. Those four counters

  — a genuine message that still decrypts after a rejection proves the receiving
  chain key did not move either.




  
  







6 · Tamper controls



  The frame MAC's preimage is label ‖ wire[0 .. 15+payload_len]
  (M1 §A.1) — the whole frame except the tag. So every
  byte-level mutation, wherever it lands, is refused before the state machine
  sees it, and all four byte-level buttons below give the same answer for the
  same reason. That sameness is the point: audit M1's defect was a MAC that did
  not cover the framing. Use the buttons on any in-flight frame above.




  The two attacks that do not modify bytes get past the MAC and have to
  be caught by the state machine instead: replay (below, and on
  any delivered frame) and reordering (deliver in-flight frames
  out of order).




Reserved msg_type — the registry, asked directly



  Flipping msg_type on the wire is caught by the MAC, so M1 §A.1
  rule 6 — "validate msg_type only after the MAC verifies"
  — is unreachable from outside without the frame key. That is the property, not
  a gap. This asks MsgType::from_u8 directly so you can see what the
  closed registry (M1 §A.2) does with a reserved byte.




  
  
  
  
  
  






Replay the handshake



  Re-feeds the captured 0x01 frame to respond. Two
  things happen and both are shown: respond accepts it and builds a
  second working session with the same session_id — it has no
  replay defence of its own, by design — and HandshakeGuard::admit
  then refuses it. The guard is the control that closes the hole, and calling it
  is a caller obligation that no type enforces (parent §6.3).
